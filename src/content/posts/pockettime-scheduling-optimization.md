이번 글에서는 학교 시간표 기반 서비스 포켓타임을 운영하며 겪은 푸시 스케줄러의 병목 현상을 DB 쿼리 개선, Redis, HTTP/2 최적화를 통해 해결한 과정을 블로그에 기록해보았습니당

![포켓타임 목업 이미지](/images/blog/pocket-time/pockettime-mockup.png)


[포켓타임](/projects/pockettime) 앱은 앱을 켜지 않아도 지금 어떤 수업 중인지, 쉬는 시간까지 몇 분 남았는지를 잠금화면(iOS 다이나믹 아일랜드 / Android 실시간 알림)에서 보여주는 기능이 있습니다. 수업이 시작되거나 끝나는 시각에 맞춰 서버에서 APNs와 FCM 푸시를 보내 UI을 갱신하는 방식을 사용합니다.

서비스 초기에는 문제가 없었지만, 사용자가 늘어나면서 피크 시간대 분당 DB 조회수가 1,000만 건까지 치솟았고 특정 시각마다 전달되어야 할 푸시 발송이 크게 지연되기 시작했습니다. 

본격적인 개선 과정을 살펴보기에 앞서, 기존 스케줄러가 어떠한 방식으로 작동했기에 이러한 부하가 발생했는지부터 살펴보겠습니다.

## 기존에는 알림 예약을 어떻게 관리하고 있었을까

초기 푸시 발송 파이프라인은 크게 **알림 예약 큐**와 **보정 스케줄러** 두 가지 축으로 동작하고 있었습니다.

![기본 스케줄 흐름](/images/blog/pocket-time/base_scheduler_flow.png)

사용자가 시간표를 등록하면 서버는 각 수업의 시작과 종료 시각을 계산해 DB의 알림 예약 테이블에 대기 작업으로 저장합니다. 이후 예약된 시각이 되면 **알림 예약 큐**에서 해당 작업을 가져와 푸시를 발송합니다.

여기에 일시적인 네트워크 순단이나 작업 지연으로 예약 발송이 누락되는 상황을 막기 위해 1분마다 전체 활성 사용자의 상태를 점검하는 **보정 스케줄러**를 함께 운영하고 있었습니다.

문제는 사용자가 늘어나면서 두 구간 모두에서 병목이 발생했다는 점입니다. 

**알림 예약 큐**에서는 시간표가 수정할 때마다 기존 예약을 조회하고 다시 등록하는 과정에서 불필요한 전체 조회가 발생했습니다.

**보정 스케줄러**에서는 상태 변화가 없는 시간에도 매분 전체 사용자를 조회하고 시간표를 다시 계산하면서 DB 부하가 누적됐습니다.

예를 들어 1교시 수업이 진행되는 50분 동안에는 잠금 화면에 표시할 수업 상태가 바뀌지 않습니다. 하지만 누락된 상태 업데이트가 있는지 확인하기 위해 같은 사용자의 시간표를 50분동안 반복해서 조회하고 있었습니다.

이러한 반복 조회가 누적되면서 정작 수업이 시작하거나 끝나는 시각에 예약하고 있는 푸시 발송까지 지연되는 문제가 발생했습니다.

## 예약 변경으로 발생하는 불필요한 작업 줄이기

사용자가 시간표를 수정하거나 시간표 제공자의 데이터가 변경되면 이전 시간표를 기준으로 등록된 알림 예약은 더 이상 유효하지 않을 수 있습니다.

따라서 이전 예약을 정리하고 새로운 시간표에 맞춰 예약을 다시 등록해야 합니다.

기존에는 이 과정에서 조회 조건을 따로 지정하지 않고 모든 사용자의 대기 예약을 DB에서 애플리케이션 메모리로 가져온 다음, 메모리에서 필요한 예약만 필터링하고 있었습니다.

예를 들어 사용자 A의 시간표가 변경되면 사용자 B의 수학 알림, 사용자 C의 영어 알림까지 모두 조회한 뒤, 전체 목록을 순회하며 사용자 A의 예약만 골라내 하나씩 삭제 요청을 보내는 방식이었습니다.

전체 대기 예약이 $Q$ 건이라면 한 번의 변경 요청에서 최대 $Q$ 건의 데이터를 읽어야 하고 동시에 $N$ 명의 사용자가 시간표를 변경하면 조회해야 하는 데이터양은 $O(N \times Q)$ 규모로 증가합니다.

이를 해결하기 위해 예약을 조회하고 삭제하는 범위를 사용자, 시간표, 시간대 기준으로 좁힌 쿼리를 작성하였습니다.

```sql
DELETE FROM scheduled_notifications
WHERE user_id = :user_id
  AND timetable_id = :timetable_id
  AND scheduled_at >= :start_at
  AND scheduled_at < :end_at;
```

변경된 SQL 쿼리 조회 조건에 맞춰 복합 인덱스도 구성했습니다. 

사용자와 시간표 처럼 특정 갚을 찾는 동등 조건을 앞에 두고 예약 시각과 같은 범위 조건을 뒤에 배치해 필요한 예약 효율적으로 탐색하도록 했습니다.

기존에 예약을 하나씩 삭제하던 방식도 Bulk Delete로 변경했습니다. 삭제 대상마다 개별 쿼리를 실행하는 대신 하나의 DELETE 문으로 묶어 DB 왕복 횟수를 줄였습니다.

이렇게 예약 변경에 필요한 데이터만 DB에서 처리하도록 변경하면서 전체 대기 예약을 메모리로 가져오는 비효율 작업을 제거할 수 있었습니다.

## 예약 갱신 과정에서 발생하는 Race Condition
예약 변경 과정의 조회 비용을 줄인 뒤에는 동시성 문제를 고려해야 했습니다.

사용자가 짧은 간격으로 시간표를 연달아 수정하면 이전 예약을 정리하는 비동기 작업과 새로운 예약을 생성하는 작업의 실행 순서가 뒤바뀔 수 있기 때문입니다. 


이를 방지하기 위해 예약 데이터에 **Generation**(Revision) 값을 추가해 작업의 실행 세대를 구분하도록 했습니다.

`Revision`은 시간표가 수정될 때마다 증가하는 값으로 예약을 생성할 떄 해당 시간표의 Revision을 함께 저장합니다. 예약을 삭제할때는 작업이 처리하는 Revision 이하의 예약만 삭제하도록 조건을 적용했습니다.

```sql
DELETE FROM scheduled_notifications
WHERE user_id = :user_id
  AND timetable_id = :timetable_id
  AND revision <= :request_revision;
```

이렇게 하면 Revision 4를 처리하던 이전 작업이 늦게 실행되더라도 Revision 5에서 생성한 예약은 삭제 대상에 포함되지 않습니다.

다만 삭제 조건에 Revision을 추가하는 것만으로는 모든 Race Condition를 방지할 수 없습니다. 

Revision 4를 처리하던 작업이 지연되었다가 Revision 5의 예약 생성이 완료된 이후에 실행되면, 이전 Revision(4)을 기준으로 한 예약을 다시 INSERT 할 수도 있기 때문입니다.

따라서 예약을 새로 등록하는 시점에도 트랜잭션 내에서 현재 시간표 테이블의 최신 Revision을 다시 조회하여 작업이 들고 있는 Revision과 일치할 때만 예약을 생성하고 불일치하면 작업을 폐기하도록 검증 로직을 추가하엿습니다.

## 실행 시각을 기준으로 푸시 발송 스케줄러 구조 개선하기
쿼리 튜닝과 Revision 도입으로 예약 변경 과정의 부하는 줄였지만, 매분 전체 활성 사용자의 시간표를 조회해 화면 업데이트 여부를 계산하는 보정 스케줄러와 RDBMS 폴링 구조의 근본적인 한계는 남아있었습니다.

수업이 진행되는 동안에는 화면에 표시할 수업 상태가 바뀌지 않기 때문에 매분 전체 사용자를 확인할 필요가 없었습니다.

예를 들어 국어 수업이 9시에 시작해 9시 50분에 끝난다면 서버가 사용자 화면 상태를 갱신해야 하는 시점은 수업이 시작하고 끝나는 두 번뿐입니다. 남은 시간은 사용자 기기에 전달해 둔 종료 시각을 기준으로 기기가 로컬에서 직접 표시하므로 수업 도중에는 서버가 별도의 푸시를 보내지 않아도 됩니다.

### Redis Sorted Set으로 푸시 발송 시각에 맞춰 예약 관리하기
DB를 지속해서 폴링하는 대신 잠금화면을 갱신해야 하는 정확한 시각에 맞춰 빠르게 작업을 꺼내오기 위해 실행 대기열의 역할을 Redis의 Sorted Set(ZSET)으로 이관했습니다.

Sorted Set은 각 원소(Member)에 Score을 부여하고 Score를 기준으로 정렬된 상태를 유지하는 자료구조입니다.

포켓타임에서는 Score에 다음 화면 갱신이 필요한 시각을 Unix Timestamp로 저장하고 Member에는 사용자 식별자와 시간표 Revision을 함께 기록했습니다. 

```redis
ZADD live_activity:scheduled 1791507600 "user:123:revision:5"
ZADD live_activity:scheduled 1791507660 "user:456:revision:2"
```

이렇게 Score에 Timestamp를 넣어두면 예약 등록 순서와 무관하게 실행 시각 순으로 자동 정렬됩니다. 스케줄러는 현재 시각을 기준으로 실행 시간이 도래한 작업만 앞에서부터 가져와 처리합니다.

```redis
ZRANGE live_activity:scheduled -inf 1791507700 BYSCORE LIMIT 0 500
```

`BYSCORE`를 통해 현재 시각(예 `1791507700`) 이하의 Score를 가진 작업만 조회하고 `LIMIT 0 500`으로 한 번에 가져올 작업 수를 제한했습니다. 이를 통해 정각처럼 특정 시각에 예약이 몰리더라도 모든 작업을 한꺼번에 메모리로 가져오지 않고 나누어 처리할 수 있도록 했습니다.

다만 `ZRANGE`는 에약을 조회할 뿐 제거하지 않기 때문에 여러 Worker가 동시에 실행되면 같은 예약을 중복으로 가져오고 처리할 수 있습니다. 조회 후 삭제(`ZREM`)하는 방식도 두 작업 사이에 다른 Worker가 접근할 수 있어 Race Condition이 발생할 가능성이 있습니다.

이 문제는 Redis Lua 스크립트로 조회와 삭제를 원자적으로 처리하는 방법을 고려할 수 있습니다.

## 다음 실행 시점만 예약하는 연쇄 스케줄링

실행 시각에 도달한 작업만 조회하도록 변경한 뒤에는 예약을 등록하는 방식도 개선했습니다.

초기처럼 하루 동안 발생할 모든 수업의 시작과 종료 시각을 미리 예약해 두면 사용자가 일과중에 시간표를 수정했을 때 남은 하루 치 예약을 모두 지우고 다시 등록해야 하는 부담이 큽니다.

이를 줄이기 위해 하루 치 예약을 한꺼번에 등록하는 대신 가장 가까운 업데이트 한 건만 예약하는 **연쇄 스케줄링** 방식을 적용했습니다. 예약된 작업이 실행되면 그 시점에 다음 상태 변경 시각을 계산해 새로운 예약을 꼬리물기 형태로 등록하는 방식입니다

```
시간표 등록
    ↓
09:00 국어 시작 예약
    ↓
09:00 작업 실행
    ├─ 국어 시작 푸시 발송
    └─ 09:50 국어 종료 예약
           ↓
       09:50 작업 실행
           ├─ 국어 종료 푸시 발송
           └─ 10:00 수학 시작 예약
```

### 중간 작업이 실패해도 다음 예약을 복구하기
연쇄 스케줄링은 현재 작업이 실행될 때 다음 작업을 등록하는 구조이기 때문에 중간에 작업이 실패하면 이후 예약이 끊길 수 있습니다. 9시 수업 시작 알림을 처리하던 Worker가 비정상 종료되면 9시 50분 수업 종료 알림이 에약되지 않아 이후 업데이트까지 누락될 수 있습니다.

!!이해안됨!!
이를 보완하기 위해 기존에 1분마다 실행되던 보정 스케줄러를 완전히 폐기하는 대신 실행 주기를 대폭 늘려 예약 누락만 점검하는 보조 Worker로 역할을 변경해 유지했습니다.

![기본 스케줄 흐름](/images/blog/pocket-time/main-sub-worker-flow.png)

평상시에는 주 스케줄러가 Redis에 등록된 예약 중 실행 시각이 도래한 작업을 빠르게 처리합니다. 반면 보조 Worker는 완화된 주기로 사용자의 시간표와 Redis 예약 상태를 대조하여 시간표상 다음 업데이트가 필요한 시각에 예약이 정상적으로 등록되어 있는지 검사합니다. 만약 이전 Worker의 중단 등으로 예약이 누락된 경우에는 해당 시간표를 기준으로 다음 작업을 다시 등록해 끊어진 예약 흐름을 복구합니다.

## HTTP 연결을 재사용 하고 처리 중인 요청 수 제어하기

스케줄러 구조를 개선한 뒤 부하 테스트에서 정각에 발송 요청이 집중되는 상황을 재현해 보니 서버의 CPU 사용률은 낮았지만 발송 큐가 빠르게 줄어들지 않았습니다.

원인을 분석해본 결과 외부 네트워크 통신과 발송 전후 DB 작업의 I/O 대기에 원인이 있다는 것을 알 수 있었습니다.

기존 APNs 발송 로직은 푸시 한건만 보낸 때마다 새로운 TLS 연결을 수립하고 앞선 요청의 응답이 끝날 때까지 다음 요청을 보내지 않는 직렬 구조로 동작하고 있었습니다.

이 방식에서는 하나의 푸시를 처리하는 동안 발생하는 네트워크 대기 시간이 다음 요청에 그대로 누적됩니다.
APNs 응답을 기다리는 데 100ms가 걸린다면 그동안 다음 요청은 시작되지 않으므로 CPU가 유휴 상태더라도 발송 큐는 직렬 처리 속도 이상으로 줄어들 수 없습니다. 

이를 위해 연결을 재사용하고 여러 요청을 병렬로 보내되 동시에 진행중인 요청 수를 제한하도록 변경했습니다.

### HTTP/2 세션을 재사용해 연결 수립 비용 줄이기

APNs Provider API가 사용하는 HTTP/2 프로토콜은 하나의 연결위에서 여러 요청과 응답을 독립적인 스트림으로 동시 처리하는 **Multiplexing**을 지원합니다. 기존 구현에서는 이 특성을 활용하지 않고 매 푸시마다 새로운 연결을 생성해 TCP 연결과 TLS Handshake 비용이 반복됐습니다.

연결을 끊지 않고 세션을 재사용하도록 변경하면서 매 요청마다 TLS Handshake를 다시 수행할 필요가 없어졌고 서로 다른 스트림을 통해 앞선 요청의 응답을 기다리는 동안에도 다른 요청을 지연 없이 전송할 수 있게 되었습니다.

### 동시 요청 수 제어와 DB 배치 처리로 I/O 최적화하기
다만 멀티플렉싱으로 요청을 동시에 보낼 수 있다고 해서 한 번에 수천 건의 스트림을 제한 없이 열면 APNs 서버의 동시 스트림 제한에 걸리거나 서버 메모리와 소켓 자원이 고갈될 수 있습니다.

이를 방지하기 위해 Semaphore를 활용해 한 시점에 동시에 처리 중인 요청수가 지정된 임계치를 넘지 않도록 동시성을 제어했습니다. 아울러 푸시 발송 전후에 개별 건마다 발생하던 DB 상태 업데이트 작업도 배치로 묶어 처리함으로써 DB왕복 횟수를 대폭 줄였습니다.

## 성능 최적화 결과
개선된 푸시 관리 파이프라인의 성능을 확인하기 위해 정각에 요청이 집중되는 상황을 재현했습니다.

외부 네트워크와 APNs 서버 상태의 변수를 통제하기 위해 TLS와 HTTP/2 통신을 재현한 자체 시뮬레이터를 사용했고 동시에 1,000건의 발송 요청이 발생하는 상황에서 개선 전후를 비교했습니다

|측정 지표|개선 전|개선 후|결과|
| --- | --- | --- | --- |
발송 지연 (p95)|101.988초|3.033초|약 97% 감소
초당 처리량|8.73건/초|335.68건/초|약 38.5배 증가
발송 누락[^1]|627건|0건|약 100% 감소
중복 발송|0건|0건|변동 없음

초당 처리량은 8.73건에서 335.68건으로 약 38.5배 증가했고 p95 발송 지연은 101.9초에서 3.03초로 감소했습니다.

기존에는 매번 전체 사용자를 조회하고 각 푸시 요청이 직렬로 처리되면서 DB 부하와 네트워크 대기 시간이 누적됐지만 Redis 기반의 연쇄 스케줄링과 HTTP/2 멀티 플렉싱 및 배치 처리를 도입하면서 대기 시간의 영향을 최소화 할 수 있었습니다. 결과적으로 피크 시간대 정각마다 몰리는 알림 트래픽을 지연이나 유실 없이 3초 이내에 안정적으로 소화하는 파이프라인을 구출할 수 있었습니다.

기존에는 각 요청이 단일로 처리되면서 네트워크 응답 대기 시간이 누정됐지만, 변경 이후에는 HTTP/2 연결을 재사용하고 여러 요청을 동시에 처리하면서 대기 시간의 영향을 줄일 수 있었습니다.
발송 전후의 DB 작업도 배치로 묶어 개별 푸시마다 발생하던 DB 왕복을 줄였습니다

[^1]: 오차범위를 벗어난 알림은 누락으로 처리
